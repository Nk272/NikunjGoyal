How GPUs Actually Run a Neural Net

A GPU is not a faster CPU — it is thousands of slow lanes marching in lockstep, starved or fed by a steep memory hierarchy. This explainer walks through the four ideas that decide whether your matmul flies or stalls: SIMT execution, the memory hierarchy, tiled GEMM, and the difference between training and inference. Drag the sliders — the cost numbers are computed live.

SIMT Execution Modelsingle instruction, multiple threads

The hardware scheduling unit is the warp: 32 threads that share one instruction pointer and execute the same instruction every cycle, each on its own data. This is "SIMT". When all 32 lanes agree, the warp runs at full width. The catch comes at a branch: if some threads take the if and others the else, the warp diverges — the hardware runs both paths serially, masking off the lanes that aren't participating. Divergence is the #1 way to silently lose throughput.

Memory Hierarchylatency & bandwidth, roughly to scale

Compute is cheap; moving bytes is expensive. Each level you climb away from the registers is an order of magnitude slower to reach. The whole art of GPU kernels is keeping data in the fast levels long enough to do lots of math on it before it gets evicted. The bars below show relative latency (cycles to first byte) and relative bandwidth (bytes/sec the level can sustain) — note how they trade off in opposite directions.

Why it matters: a global-memory load can cost 400–500 cycles. If the warp scheduler can't find other warps with ready work to hide that latency, the SM stalls. Tiling (next tab) exists precisely to turn slow global traffic into fast on-chip shared-memory reuse.
Tiled Matrix Multiply (GEMM)C = A · B, the heart of every layer

Every dense layer, attention projection, and conv-as-matmul is a GEMM. A naive kernel re-reads each row of A and column of B from slow global memory for every output element. A tiled kernel loads a small block of A and B into shared memory once, then every thread in the block reuses it — slashing global traffic by roughly the tile dimension.

$$ \text{Arithmetic Intensity} = \frac{\text{FLOPs}}{\text{Bytes moved}} \;\propto\; \text{tile size } T $$

Inference vs Trainingforward, backward, KV-cache & batching

Training runs a forward pass, then a backward pass that is ~2× the forward cost and must stash every activation for the gradient — so memory and compute both balloon. Inference is forward-only. For an autoregressive LLM, the key trick is the KV-cache: keys and values for past tokens are computed once and reused, turning per-token work from quadratic re-computation into a cheap append.

The batching tradeoff: decode is memory-bound — you re-read the entire weight matrix to generate one token, so a single request barely uses the FLOPs. Batching many requests amortizes that weight read across the batch, raising throughput dramatically while per-request latency stays nearly flat — until the KV-cache eats all your VRAM and you can't fit more concurrent sequences. That ceiling is why long-context serving is hard.
